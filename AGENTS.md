# Entwicklung und Freigaben

- `main` ist der gemeinsame Integrationsbranch. Neue Features auf `ft/*`, Fehlerkorrekturen auf `fix/*`, andere Aufgaben auf einem sachlich passenden Arbeitsbranch entwickeln und über einen geprüften GitHub-PR nach `main` integrieren. Neue Branches niemals mit `codex/` beginnen; bestehende Branches nicht allein deshalb umbenennen.
- Vor dem Merge: `npm test`, `npm run check` und die betroffenen Browser-Szenarien (`npm run test:browser -- --group=…`). Main ist auf GitHub durch PR-Pflicht und den Check `verify` geschützt, auch für Administratoren. Lokal nur den gemergten Remote-Stand mit `git fetch origin` und Fast-Forward übernehmen. Keine erzwungenen Pushes; bestehende Release-Tags niemals verändern.
- Stable und Experimental sind nur Release-Streams des Updaters; jedes Paket enthält eine Laufzeit. Experimentelles Verhalten nur hinter Feature-Schaltern in `extension/features.js`, die im Stable-Profil aus und in beiden Profilen getestet sind. Nicht sicher abschaltbare Umbauten bleiben auf einem regelmäßig mit Main abgeglichenen `experiment/*`-Branch mit Draft-PR.
- Jeder erfolgreiche Main-Build veröffentlicht einen Experimental-Kandidaten `vX.Y.Z-preview.N`. Branches sind keine Update-Kanäle; PR-Builds veröffentlichen keine Nutzer-Updates. Signiert und veröffentlicht wird nur in Jobs der geschützten GitHub-Umgebung `release` (Secret `RELEASE_SIGNING_KEY`); andere Jobs lesen keine Secrets. Actions in `.github/workflows/` nur per vollständigem Commit-SHA mit Versionskommentar einbinden.
- Stable nur nach ausdrücklichem Auftrag des Eigentümers und praktischer Abnahme des exakten Kandidaten einschließlich seines Stable-Pakets: `npm run promote -- stable --candidate vX.Y.Z-preview.N --tested <vollständiger-Commit>`. Das kopiert bereits gebaute, per GitHub-Prüfsumme und CI-Signatur verifizierte Dateien und signiert sie als Stable-Update; kein Neubau. Lokal den Schlüssel nur über `RELEASE_SIGNING_KEY_FILE` angeben, ihn nie lesen, kopieren, ausgeben oder committen. Workflow-Umstellungen und grüne Tests sind keine Stable-Abnahme.
- Automatische GitHub-Updateprüfungen laufen alle **30 Minuten** (Chrome-Alarm `UPDATE_INTERVAL_MINUTES`) sowie beim Browserstart, Kanalwechsel und Öffnen des Popups. Alle automatischen Auslöser teilen in `checkUpdates` eine kurze Sperre von **2 Minuten** (`AUTOMATIC_DEBOUNCE_MINUTES`), gemessen ab dem Start der vorherigen Prüfung; die Sperre muss deutlich kürzer als der Alarm bleiben, damit kein Alarm übersprungen wird. Bestehende Installationen übernehmen den Takt beim Update. Installiert wird nur nach Nutzerklick und nur mit gültiger Release-Signatur (`extension/release-key.js`).
- `npm run dev` startet den lokalen Helfer und erzeugt `dist/development/extension`; diesen Ordner einmal als „Video Sync · Dev“ laden. Nur dort erscheint bei laufendem Helfer zusätzlich „Dev · <ausgecheckter Branch>“; Änderungen und Branchwechsel werden nach erfolgreicher Buildprüfung nur im ausgewählten Dev-Kanal automatisch aktiviert (pausierbar). Normale Pakete zeigen nur Stable/Experimental und enthalten keinen Dev-Verbindungsclient. Ohne Helfer verschwindet ein ungewählter Dev-Eintrag; ein ausgewählter bleibt offline. Der Helfer schaltet keinen Git-Branch um und verwendet je Checkout einen eigenen Loopback-Port. Räume/Video werden beim Dev-Reload bestmöglich wieder verbunden; Wiedergabe bleibt pausiert, erneutes Ausrichten kann nötig sein.
- Persönliche Testbrowser mit `npm run manual-test` starten: standardmäßig eine Kopie des ausgecheckten `extension/` mit Profil und Kanal `stable`. Ein freigegebener Stand wird über `TEST_EXTENSION=<entpacktes Release>/video-sync/extension` getestet, Experimental nur bei ausdrücklich gewünschtem Test (`TEST_CHANNEL=experimental`). Bestehende Browserpfade aus der lokalen Git-Konfiguration verwenden.
- Der normale Nutzerserver auf `localhost:8787` wird auch außerhalb der Tests benutzt. Ihn niemals stoppen; nur eigens gestartete temporäre Testserver beenden.
- Das Remote `origin` ist das öffentliche Repository `https://github.com/mikastudhhn/chrome-extension-video` unter MIT-Lizenz (Name und Commit-Adressen des Nutzers sind sichtbar; akzeptiert). Keine Einladungen, Server-Deployments oder Sichtbarkeitsänderungen ohne entsprechenden Nutzerauftrag.
